# 首次共享启动竞态修复

基线 `77aecce`；仅调整桌面共享启动事务与回归测试。帧率、分辨率、编码、码率策略和服务器均未修改。

## 证实的问题

原启动流程先发布视频并显示本地预览，再等待独立系统音频，最后标为共享。等待期间仍用最初的 `socket.id` 判断整个任务是否有效。信令暂断时 Socket.IO 可临时清空 ID；即使媒体代次、transport 和视频 producer 仍有效，后续检查也会取消并关闭已发布视频。取消路径还可能留下指向 ended track 的本地预览引用。

这个时序可确定性复现出“出现预览后撤回，需再开始”的结果。对用户现场那一次的原始失败，没有保留下来的结束事件可证明唯一触发原因；不将静态可能性或模拟当成完整现场复现。

## 修复边界

- 视频提交前仍校验原信令身份，不能让过期捕获发布。
- 视频提交后使用当前 publication/media 代次、同一 transport 和当前未关闭 producer 判断所有权。信令暂断不再让附属音频撤销健康视频。
- 音频保留原独立信令检查，取消时只释放自己的资源。锁存启动期间见过的信令中断，避免清理完成前已恢复相同 ID 时误报普通错误。
- 不提前改变 `isSharing` 的 UI 时机，不开放重复启动或并发参数更新，不自动增加新的采集/音频恢复。
- 真正停止、离房、transport 替换或会话失效仍撤销旧任务；清理已采用的预览时验证所有权，不影响新共享。
- 只保留固定字段的启动取消日志：阶段和四种代次/连接变化布尔值。临时 stack trace 和 native 诊断 imports 已删除，无画面、token、SDP 或用户内容记录。
