# Cove 客户端 UI 审查

## 审查范围

- 流程：首次进入 → 空房间列表 → 创建房间 → 房主进入房间并管理成员 → 页面刷新/重连。
- 画面：桌面端 1280×720，本次审查实际捕获的 Cove 客户端。
- 用户目标：3–4 位朋友尽快进入语音、共享屏幕，并让房主安全地管理房间。
- 可访问性目标：识别明显的 WCAG AA 风险；截图不能证明完整合规。

## 做得好的地方

- 暗色、低干扰的视觉方向适合朋友语音和长时间屏幕共享。
- 创建房间流程很短，没有不必要的配置。
- 房主皇冠、禁言按钮和成员状态集中在成员列表中，权限归属容易理解。
- 界面结构不复杂，继续迭代不需要推翻现有设计语言。

## 主要问题

### P0：刷新/重连状态被误呈现为“成员为 0”

步骤 5 中聊天记录仍然存在，但成员数变成 0，删除按钮和房主身份也暂时消失。界面没有说明正在重连、同步失败还是成员确实离开。这会直接破坏语音工具最重要的“当前状态可信度”。

建议引入明确的房间同步状态：`正在连接`、`正在恢复房间`、`已连接`、`连接中断`。同步完成前保留上一次成员快照并降低透明度，不要直接显示 0；同时暂时禁用禁言、删除和媒体控制。

### P1：高频媒体操作的层级低于低频管理操作

步骤 4 中“删除”和“禁言”是醒目的文字按钮，而“加入语音”在左下角，“共享屏幕”只有加入语音后才出现。用户进入房间后的主要目标是开始通话或看共享，而不是管理房间。

建议把底部改成常驻的媒体控制台：主按钮为“加入通话”，进入后原位变成麦克风、共享屏幕、系统音频和离开。连接质量使用一个小型状态胶囊展示；房间删除移入房间菜单。

### P1：屏幕共享应该成为房间的主舞台

当前结构的中心区域默认是聊天，屏幕共享只是聊天上方的一块区域。对 Cove 的核心需求而言，共享发生时应切换布局：共享画面占据中心主舞台，聊天收进可折叠右侧抽屉，成员和媒体控制保持可见。

建议使用两种布局状态：

- 未共享：聊天为主，成员栏可折叠。
- 正在共享：画面为主，聊天变成右侧抽屉，底部悬浮媒体控制台。

### P1：侧栏承载了过多不同任务

成员、语音包、房主操作和媒体入口都堆在同一窄侧栏，重要性相互竞争。语音包属于娱乐型次要功能，不应长期占据固定空间。

建议成员列表常驻；语音包改成工具栏按钮或底部弹出面板；房主操作放入成员行的更多菜单，只在悬停或聚焦时出现。

### P1：危险操作缺少足够的层级保护

“删除”紧贴房间标题且始终为红色，容易误触；“禁言”文案也没有说明它只影响语音。

建议删除房间移入 `…` 菜单，二次确认明确写出会删除聊天记录；禁言改为“语音禁言”，操作后出现可撤销提示，并在成员头像旁持续显示状态。

### P2：首次进入暴露了技术配置

服务器地址与用户名处于同一主层级。朋友第一次使用时并不关心服务器/隧道概念，只需要加入你给出的 Cove。

建议默认隐藏服务器地址，提供“高级设置”展开项；后续可增加邀请链接或邀请码，自动写入服务器地址和房间信息。

### P2：视觉状态和图标语言不够统一

界面混用 Emoji、文字、SVG 和符号图标。在线状态、房主、禁言、共享和网络质量也没有统一的颜色语义。

建议保留现有 zinc/black 视觉体系，只增加一套稳定语义：绿色代表已连接/说话，青色代表共享/媒体，琥珀色代表房主，红色只用于错误和破坏性操作。图标统一使用同一个图标库。

## 可访问性风险

- 多处 `white/30`、`white/40` 的小字号文字在截图中对比度偏低，需要实际测量后提升。
- 房间页的返回、折叠侧栏和发送按钮在 DOM 中没有可读名称，屏幕阅读器难以理解。
- 登录表单主要依赖占位符识别，视觉标签与输入框的程序化关联需要检查。
- 截图无法验证键盘焦点、Tab 顺序、对话框焦点锁定、缩放重排和动态状态播报。

## 推荐落地顺序

1. 先修复重连/同步状态，保证成员数和房主权限不会短暂显示错误。
2. 建立常驻媒体控制台，并让共享状态切换为“画面主舞台”。
3. 重组侧栏，把语音包和房主低频操作收进次级面板或菜单。
4. 统一图标、颜色语义、可访问名称和文字对比度。
5. 最后简化首次进入，把服务器地址放进高级设置或邀请流程。

## 证据限制

本次没有接受麦克风/屏幕权限，因此未捕获加入语音后的控制台、共享选择器和实际共享画面；这些状态仍需要单独做一次媒体流程审查。
